    3行サマリ

    • RAGは、全文をプロンプトへ詰め込む代わりに、候補検索と再ランキングで必要な知識だけを取り出し、知識カットオフ・長文での注意散漫・入力コストを同時に緩和する。
    • Tool CallingはLLMに関数を直接実行させる仕組みではなく、LLMがツールと引数を選び、外部実行結果を再びLLMへ渡す制御ループである。Tool SelectionとMCPが、多数ツールの選択と公開方法を整える。
    • AgentはObserve → Plan → Actを繰り返して目標を追うが、各段階の誤りが累積する。小さく始め、最強モデルで上限を確認し、推論過程を観察できる状態を保つことが実践上の要点となる。

    このレポートの論理構成

    「LLMに何が足りないか」を起点に、知識を補う仕組み、行動を可能にする仕組み、自律性を高めたときの統制へ順番に進む。

    Phase 1 · Sections 1–2 課題を定義する

    知識の鮮度と行動能力という、単体LLMの2つの不足を切り分ける。

    Phase 2 · Sections 3–11 知識を補う

    RAGを、準備・候補検索・改善・再ランキング・評価の順に組み立てる。

    Phase 3 · Sections 12–14 行動能力を与える

    Tool Callingから、tool選択、MCPによる接続標準化へ拡張する。

    Phase 4 · Sections 15–17 自律性を広げ、統制する

    ReAct、Multi-Agentへ進み、最後に安全性と実装原則を整理する。

    1. 講義の射程：LLMを外部世界へ接続する

    このセクションで説明すること

    講義全体の目的、前回のreasoning modelとのつながり、今回扱うRAG・Tool Calling・Agentsの役割を最初に俯瞰する。

    ここで全体像を定めた後、次節では最初の課題である「知識をどう最新化するか」を具体的に掘り下げる。

    講義の3本柱は RAG、Tool Calling、Agents。これまで単独で推論していたLLMを、更新され続ける知識と実行可能な機能へつなぐ。

    前回Lecture 6の短い振り返り

    冒頭ではreasoning modelとGRPOを振り返る。同一プロンプトから複数のcompletionを生成し、グループ内の相対報酬でadvantageを作るため、PPOのような独立したvalue modelを不要にできる。一方で、学習性能が頭打ちになった後も出力長が伸びるlength biasがあり、DAPOやDr. GRPOのような正規化方法の見直しが必要だった。

    今回扱う弱点 1

    重みの学習時点より後の出来事や、組織固有の知識を直接は持たない。

    今回扱う弱点 2

    文章を生成するだけでは、検索・計算・送信・設定変更などの行動を完遂できない。

    解決の方向

    前者をRAG、後者をTool CallingとAgentで補い、MCP/A2Aで接続方法を標準化する。

    2. なぜRAGが必要なのか

    このセクションで説明すること

    知識カットオフ、context上限、長文中の注意散漫、入力コストを整理し、再学習や全文投入ではなぜ十分でないかを示す。

    第1節で示した「知識の不足」を問題として定式化し、次節のRAGパイプラインが必要になる理由を作る。

    モデルの再学習や「全部プロンプトに入れる」方法は、更新性・精度・費用のいずれにも弱点がある。

    素朴な方法 / 制約問題講義での具体化
    重みへ知識を追加学習既存能力のregressionが起こり得る。複数の用途別fine-tuneがあると、すべてを再更新する必要がある。更新のたびに学習・評価・配備を繰り返すのは保守負荷が大きい。
    全情報をpromptへ投入context windowを使い切り、長い入力ほど費用も増える。講義時点のGPT-5は400,000 tokens。数百ページ規模でも上限は有限。
    長いcontextに頼る無関係情報が多いと必要な事実を見失う。Needle in a Haystackテストでは、長さと事実の位置の両方が取得精度へ影響。
    毎回大きなinputを送るtoken課金が積み上がる。講義ではGPT-5入力価格を「100万tokenあたり約1ドルのオーダー」と説明。
    重要な含意：context windowが大きいことと、必要情報を正確に使えることは同義ではない。RAGでは「何を取得するか」が生成品質の上限を決める。

    3. RAGの基本パイプライン

    このセクションで説明すること

    文書の準備から候補取得、再ランキング、prompt拡張、回答生成まで、RAGを構成する処理を一枚の流れとして把握する。

    前節で確認した制約への解答を先に全体図で示し、第4〜11節ではこの図を左から順に分解していく。

    RAG = Retrieval-Augmented Generation。ユーザーの質問に関連する情報を取得し、その情報でpromptを拡張してから回答を生成する。検索に失敗すれば、生成段階で正しい答えを作る材料そのものが欠ける。

    flowchart LR D[文書群] --> C[Chunking] C --> E[Chunk Embedding] E --> V[(Knowledge Base)] Q[User Query] --> QE[Query Embedding] QE --> R[Candidate Retrieval] V --> R R --> RR[Cross-encoderで再ランキング] RR --> K[Top-K Chunks] K --> A[Promptを拡張] Q --> A A --> L[LLM] L --> O[Response]

    流れは大きく2つに分かれる。事前処理では文書をchunk化してembeddingとともにknowledge baseへ保存する。問い合わせ時にはqueryを表現へ変換して候補を探し、必要なら高価なrerankerで並べ替え、上位chunkだけをLLMへ渡す。

    4. Knowledge Base：chunking・embedding・保存

    このセクションで説明すること

    RAGの事前準備として、文書をどの単位で分け、どの表現へ変換し、検索可能なknowledge baseとして保存するかを整理する。

    第3節の全体図にあるoffline側を具体化する。検索対象が整ったところで、次節からonline側のretrieval設計へ進む。

    設計項目講義中の目安トレードオフ
    Embedding次元約1,500次元のオーダー大きいほど表現力を持てる一方、保存容量と検索計算量が増える。
    Chunk size約500 tokensなど数百token小さすぎると文脈を失い、大きすぎると一つの表現へ複数トピックが混ざる。
    Overlap前後に低い数百token境界をまたぐ意味を保持できるが、保存量と候補重複が増える。
    Chunk境界固定長だけに限定しないJSONやMarkdownなどの構造を尊重すると、意味単位を壊しにくい。
    Embedding model事前学習済みまたは独自学習汎用性・導入速度と、ドメイン適合性の間で選ぶ。

    質問への回答に必要なchunkをground truthとして用意できるなら、検索品質を定量評価できる。chunk設計は単なる前処理ではなく、後段のretrievalが選べる情報単位そのものを決める。

    5. Two-Stage Retrieval：まず広く、次に精密に

    このセクションで説明すること

    大規模なknowledge baseを、低コストな候補取得と高精度な再ランキングの2段階へ分ける理由を説明する。

    第4節で用意したchunkをどう絞るかというonline検索の設計図であり、第6・7節でStage 1、第10節でStage 2を詳しく見る。

    検索・推薦システムと同様、RAGでも全chunkへ高価なモデルを適用するのではなく、候補取得とランキングを分ける。

    Stage 1: Candidate Retrieval

    数千〜数百万のchunkから、semantic searchやBM25で約100件の候補へ絞る。取りこぼしを減らすrecall重視。

    Stage 2: Ranking / Reranking

    候補だけにqueryとの詳細な相互作用を計算し、LLMへ渡すTop-Kを決める。precisionと順位品質を重視。

    6. Dense Retrieval：SBERTとBi-encoder

    このセクションで説明すること

    Stage 1の第1手法として、queryとchunkをembedding化し、意味的な近さで候補を高速取得する仕組みを説明する。

    Two-Stage Retrievalの候補取得をsemantic searchで実装する。次節では、意味検索が苦手な完全一致をBM25で補う。

    queryと各chunkを別々にencoderへ通し、embedding間のcosine similarityを計算する。chunk側は事前計算できるため高速で、queryごとに全モデル推論を繰り返さずに済む。

    SBERTの役割

    Sentence-BERTはBERTを文・シーケンスレベルのembedding生成へ適応する。関連ペアのcosine similarityを高くし、非関連ペアを低くするよう学習する。講義ではSBERT論文とドキュメントの一読を強く勧める。

    • knowledge baseが巨大なら線形な全件比較は重い。FAISSなどのApproximate Nearest Neighbor手法で探索を近似・高速化する。
    • Q&Aでは、既定の距離としてcosine similarityが一般的と説明。embeddingをunit normへ正規化すればL2距離と密接に対応する。

    7. BM25とハイブリッド検索

    このセクションで説明すること

    Stage 1の第2手法として、語の一致を重視するBM25を取り上げ、dense retrievalと組み合わせる理由を示す。

    第6節のsemantic searchだけでは固有名詞を外し得るためlexical searchを加える。次節では、候補検索の入力表現そのものを改善する。

    embedding検索は意味的な近さを捉えるが、固有名詞・型番・完全一致が重要な場面では外すことがある。BM25はqueryと文書の語の重なりを用いるlexicalなヒューリスティックで、この弱点を補う。

    Cuddly と Huggy の例

    ユーザーが「Cuddly」という名前のテディベアを探しているとする。semantic searchは意味の近い「Huggy」を上位にする可能性があるが、BM25は文字列としてCuddlyを正確に拾える。実務ではdense retrievalとBM25を組み合わせるhybrid searchがよく使われる。

    検索方式強み弱み向く対象
    Dense / Semantic言い換えや意味の近さを拾う固有名詞の完全一致を保証しない自然言語の質問、概念検索
    BM25 / Lexical語の一致に強く、説明可能言い換えや同義語に弱い名前、型番、専門用語
    Hybridsemanticとlexicalの相補性を使うスコア統合や重み調整が必要一般的な本番RAG

    8. HyDEとContextual Retrieval

    このセクションで説明すること

    問い合わせ時にqueryと文書の表現差を埋めるHyDEと、索引構築時にchunkが失った文脈を補うContextual Retrievalを区別して説明する。

    第6・7節で検索方式をそろえた後、query側とchunk側の入力品質をそれぞれ高める。Contextual Retrievalは索引構築時の反復計算を増やすため、次節でPrompt Cachingを扱う。

    HyDE：queryを仮想文書へ変換する

    短い疑問文のqueryと、長い説明文のchunkは性質が異なる。同じencoderで比較しづらいなら、LLMにqueryへの仮想的な回答文書を生成させ、その文書をembeddingして本物の文書と比較する。これがHypothetical Document Embedding（HyDE）である。

    HyDEは常に効くとは限らず、講義も「効くかもしれないし、効かないかもしれない」として実験を勧める。別案はquery encoderとdocument encoderを別々に学習することだが、学習と保守の負担が増える。

    Contextual Retrieval：chunkへ文書全体の文脈を足す

    機械的に切ったchunkは、「それ」「この結果」の参照先や章全体のテーマを失う。文書全体と対象chunkをLLMへ渡し、「このchunkを理解するために必要な短い文脈」を生成して先頭へ付加すれば、embeddingとBM25の両方が扱いやすくなる。

    代償：すべてのchunkについて文書全体を含むLLM呼び出しが必要になる。この反復計算を現実的にするのが、次のPrompt Cachingである。

    9. Prompt Caching：共通prefixの計算を再利用する

    このセクションで説明すること

    同一prefixの内部計算を再利用し、Contextual Retrievalの索引構築で発生する大量の類似promptを低コストで処理する仕組みを説明する。

    第8節でchunk品質の向上と引き換えに増えたoffline前処理の計算量を抑える。検索候補の準備と取得方法がそろったところで、次節はStage 2の精密な再ランキングへ進む。

    decoder-only LLMはleft-to-rightに計算するため、同じprefixなら各layerの内部状態も同じになる。共通prefixのactivationを一度保存し、次の呼び出しで再利用すれば、Contextual Retrievalのような反復処理を安くできる。

    10. Cross-encoderで候補を再ランキングする

    このセクションで説明すること

    Stage 1で集めた候補へqueryとの詳細な相互作用を計算し、LLMへ渡すTop-Kの順序を精密化する方法を説明する。

    第5節で分けたStage 2をここで完成させる。検索pipelineがそろったため、次節では良し悪しを測る評価指標へ進む。

    bi-encoderはqueryとchunkを独立に表現するため高速だが、両者のtoken間の細かな相互作用は見ない。cross-encoderはqueryとchunkを同時に入力し、attentionを通じて関連度を直接推定する。

    観点Bi-encoderCross-encoder
    入力QueryとChunkを別々にencodeQuery + Chunkを一緒にencode
    相互作用完成したembedding間の距離モデル内部でtoken間attentionを計算
    事前計算Chunk embeddingを保存可能Queryごと・Chunkごとに推論が必要
    計算量低い高い
    主な段階Stage 1 Candidate RetrievalStage 2 Reranking

    rerankerには事前学習済みモデルも、用途別に学習したモデルも使える。候補全体ではなくStage 1で絞った集合だけへ適用することで、精度と費用のバランスを取る。

    11. Retrievalをどう評価するか

    このセクションで説明すること

    NDCG、MRR、Recall@K、Precision@Kを使い、候補の取りこぼしと上位順位の品質をどのように測るかを整理する。

    第3〜10節で構築したRAGを評価可能なsystemとして閉じる。知識を補う議論を終え、次節から第2の課題である「行動能力」へ移る。

    「上位K件へ本当に関連chunkが入ったか」をground truth labelと比較する。講義は、論文で頻出するNDCG、MRR、Recall@K、Precision@Kの4指標を押さえるよう勧める。

    DCG@K = Σi=1..K reli / log2(i + 1) NDCG@K = DCG@K / IDCG@K。IDCGは関連文書を理想順に並べたときのDCG。
    指標定義何を重視するか
    NDCG@K順位でdiscountしたgainを理想順位のDCGで正規化複数の関連文書をどれだけ上位へ並べたか。理想なら1.0。
    MRR各queryで最初の関連文書の順位の逆数を平均最初の正解へどれだけ早く到達するか。2位ならRR=1/2。
    Recall@KTop-Kに入った関連文書数 / 全関連文書数取りこぼしの少なさ。Stage 1で特に重要。
    Precision@KTop-Kに入った関連文書数 / K取得結果の純度。LLMへ無関係情報を渡さない度合い。

    MTEB（Massive Text Embedding Benchmark）はretrieverやembeddingを比較する代表的ベンチマークとして紹介される。ただし本番用途では、自分のquery分布と関連ラベルを使った評価が必要である。

    12. Tool Calling：構造化機能をLLMへ開く

    このセクションで説明すること

    LLMがtoolと引数を選び、外部実行結果から最終回答を作る3段階のloopと、それをSFTまたは説明最適化で成立させる方法を説明する。

    RAGが「読む」能力を補ったのに対し、ここからは「実行する」能力を扱う。toolが増えたときの選択問題を次節へ引き継ぐ。

    RAGが非構造文書から情報を取り出すのに対し、Tool Callingは関数として表せる構造化データや行動を扱う。

    講義は「自律システムが外部resourceへ動的にaccessし、必要なら作用することで複雑なtaskを完遂する能力」という定義を採用する。重要なのは、LLM自身が関数の実装を行うのではなく、どの関数をどの引数で呼ぶかを予測する点である。

    sequenceDiagram participant U as User participant L as LLM participant O as Orchestrator participant T as External Tool U->>L: Query + Tool schema / explanation L-->>O: Tool名と引数を予測 O->>T: 関数を実行 T-->>O: 構造化結果 O->>L: 会話履歴 + Tool結果 L-->>U: 自然言語の最終回答

    Tool Callingの3段階

    1. 引数推定：toolの名前、入力・出力schema、説明とuser queryから、LLMが呼び出しを構造化して出力する。「近くのbear」なら既知の現在位置を座標へ変換する。
    2. 外部実行：orchestratorが通常のコードとして関数を実行する。この段階はLLM推論ではない。
    3. 回答生成：構造化結果と会話履歴をLLMへ戻し、ユーザー向けの文面へ整える。

    学習する場合：2種類のSFT pair

    • Tool prediction pair：query + function API → 適切なtool名と引数。
    • Response generation pair：元のquery、tool call、tool resultを含む会話履歴 → 所望形式の最終回答。

    データは「near me」「Parisで探す」、明示座標、複数tool、multi-turnなど、実ユーザー分布を反映して多様にする。2つ目のpairはJSONだけの言い換えではなく、tool resultがどのqueryとcallに対応するかを含む履歴全体を入力する。

    SFTせず、tool説明を最適化する場合

    近年のLLMはコードを大量に学習しており、tool schemaと説明だけでも呼び出せる場合がある。講義は、望ましいtool call pairを評価セットにし、現在の説明で成功・失敗を測り、その結果をreasoning modelへ渡して説明を書き直させる反復を提案する。これはofflineで行い、inference時には固定した説明をschemaとともに渡す。

    Toolの種類例主なリスク
    情報取得ニュース、天気、株価、在庫古い値、誤った引数、sourceの信頼性
    計算queryをコードへ変換して実行生成コードの誤り、実行環境の権限
    行動メール送信、予約、設定変更不可逆操作、権限濫用、data exfiltration

    13. Tool Selection：大量のtoolから必要なものだけを渡す

    このセクションで説明すること

    すべてのAPI定義をpromptへ詰め込まず、routerで候補toolを先に絞る2段階方式を説明する。

    第12節のTool Callingを多数toolへ拡張すると選択とcontextの問題が生じる。選んだtoolを共通形式で接続する方法が次節のMCPである。

    すべての完全なAPI定義をpromptへ並べると、tool版Needle in a Haystack、context window消費、latency増加が起きる。講義はGoogle DeepMindのTool Selectorを例に、2段階のrouter方式を紹介する。

    1. 全toolの名前と短い説明だけを見て、関連toolを選ぶ。
    2. 選択されたtoolの完全なAPI schemaだけをcontextへ入れ、通常のTool Callingを行う。

    Q&Aでは「これはRAGではないか」と問われ、RAGで実装することもできるが、それだけに限定されないと回答する。目的はlatencyと選択精度の両方を改善することにある。

    14. MCP：tool公開を標準化する

    このセクションで説明すること

    MCP Host・Client・Server・Tools・Prompts・Resourcesの役割を分け、外部能力を発見・記述・接続する共通形式を説明する。

    第13節で「どれを使うか」を決めた後、ここで「どう接続するか」をそろえる。tool基盤が整ったため、次節では複数回の実行を自律的につなぐAgentへ進む。

    toolごとに独自schema・接続方式を用意すると再利用できない。Anthropic発のModel Context Protocol（MCP）は、LLM hostと外部能力をつなぐ共通語彙と接続方法を定める。

    構成要素講義での役割書籍推薦の例
    MCP HostLLMを含むユーザー向けアプリClaudeなどのLLM host
    MCP ClientHost内で1つのServerと1対1に接続するインフラ書籍provider serverへの接続
    MCP Server能力を提供するinstance書籍providerが運営
    Tools実行できる関数実装find_books、recommend_books
    Promptstoolの使い方を示すtemplatetitle検索、嗜好に沿った推薦
    Resourcestaskに使える外部データ個人collection、人気書籍ranking

    MCPは「どのtoolを使うべきか」という推論そのものを解決するのではなく、能力を発見・記述・接続する方法をそろえる。Tool Selectionと組み合わせて、必要な能力だけをLLMへ提示する。

    15. AgentとReAct：目標まで推論と行動を反復する

    このセクションで説明すること

    単発のTool CallingをObserve → Plan → Actの反復loopへ拡張し、途中結果に応じて次の行動を変えるReActの考え方を説明する。

    第12〜14節で用意したtoolを、一つの目標へ向けて繰り返し使う段階である。次節ではこのloopを複数Agentの協調へ広げる。

    講義におけるAgentは、ユーザーに代わって自律的に目標を追い、taskを遂行するsystemである。単発のTool Callingとの違いは、結果を観察して次の行動を決めるrecursive loopにある。

    flowchart LR I[User Goal] --> O[Observe] O --> P[Plan] P --> A[Act / Tool Call] A --> R[Result] R --> G{Goal reached?} G -- No --> O G -- Yes --> F[Final Output]
    「テディベアが寒がっている。何かして」
    1. Observe：寒いことは分かるが、現在温度が不明。Plan：室温を確認する。Act：get_current_room_temperature() → 65°F。
    2. Observe：65°Fは期待より低い。Plan：温度を上げる。Act：adjust_temperature(increase=5)。
    3. Observe：設定変更が完了。目標達成としてループを止め、「温度を5°上げました」と回答する。

    複雑なtaskをatomicなstepへ分解し、各tool resultを次の状態として使う点が本質である。最初から固定されたcall列を実行するのではなく、観測によって経路が変わる。

    16. Multi-AgentとA2A

    このセクションで説明すること

    専門性の異なるAgentを分業させる構成と、skill公開・task状態・cancelを標準化するA2A Protocolの役割を説明する。

    第15節の単一Agent loopを協調systemへ拡張する。構成要素と実行回数が増えるほど誤りと攻撃面も増えるため、次節で安全性と運用原則を扱う。

    室温管理を例にすると、thermostat、energy management、air qualityなどを独立Agentに分け、互いの出力を使って協調できる。各Agentは固有のcontextと推論loopを持ち、他Agentとはinput/outputを介して通信する。

    分業

    異なるtool・policy・専門知識を持つAgentへ責務を分ける。

    通信

    GoogleのAgent-to-Agent（A2A）Protocolはskill公開、task status、cancelなどの通信を標準化する。

    予算

    Q&Aではtoken budgetはAgent間で自動共有されないと説明。ただし複数Agentの金銭コストは合計される。

    MCPがHostとtool providerの境界をそろえるのに対し、A2AはAgent同士の能力発見とtask協調をそろえる、という役割分担で理解できる。

    17. 安全性、誤りの累積、実践上の助言

    このセクションで説明すること

    Agentが現実世界へ作用することで生じるdata exfiltration、stepごとの誤りの累積、training・inference・evaluation・operationsの対策を整理する。

    知識取得、tool接続、自律loop、複数Agentへと能力を増やしてきた流れを、最後に「安全に構築・評価・改善するには何が必要か」という実装原則へ着地させる。

    外部世界へ作用できる能力は、文章生成だけのモデルにはなかった被害を生む。講義の代表例は、公開可能なメールtoolを使ってpasswordを外部へ送らせるdata exfiltrationである。

    対策層講義での方法狙い
    Training-timeSFT/RLのdata mixtureへ安全・harmlessnessの例を含める危険なtool useや要求をモデルのpolicy自体で避ける。
    Inference-timeSafety classifierでquery、tool call、outputを監視運用時に危険な入力・出力をblockまたはreviewへ回す。
    EvaluationToolSword、Agent Safety Benchなどでhazardを測る正常taskの成功率だけでなく、悪用耐性を定量化する。
    Operations最小権限、確認、trace、取消可能性を持たせる誤りが現実の不可逆操作へ直結する範囲を狭める。

    講義前日に公開されたAnthropicのcyber attack報告にも触れ、Agent能力は攻撃側にも使われるが、防御側も高度化できるため「負け戦ではない」と述べる。ただし対策なしに能力だけを追加してはならない。

    Error Compounding

    Agentは引数推定、tool選択、実行結果のgrounding、次stepの計画を何度も繰り返す。各stepが高精度でも、長いchainでは誤りが累積する。講師はこれを「大規模Agentがまだ世界を支配していない理由」の一つとして説明する。

    構築時の3つの助言
    1. Start small：「最寄りのbearを探す」のような単純taskからpromptと実装を確認する。
    2. Start smart：最初は最も能力の高いmodelでheadroomを確認し、正しさを確立してからlatency・costを最適化する。
    3. Debuggability：推論chainとtool traceを観察し、どのstepで判断が崩れたか追えるようにする。

    締め：コード生成より、正しさを判断するtaste

    講師が現在もっとも気に入っているAgent用途はAI coding assistantである。定型作業を委譲してmental loadを減らせる一方、基礎的なcodingを学ばなくてよいわけではない。「コード生成は安くなるが、そのコードが正しく意図どおりかを判断するtasteがもっとも重要になる」という言葉で講義を閉じる。次回はevaluation landscapeを扱う。

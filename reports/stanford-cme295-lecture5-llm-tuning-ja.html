    3 行サマリ

    • 教師あり微調整（SFT）は「この答えを出してほしい」は教えられるが、「この答えは避けてほしい」を直接は教えにくい。そこで、同じ質問への 2 つの答えを比べた選好ペアを使い、望ましい答えの確率を相対的に高める。
    • 人間のフィードバックからの強化学習（RLHF）は、選好から採点器を学ぶ段階と、その点数で言語モデルを更新する段階に分かれる。代表的な PPO は強力だが、policy・value・reward・reference の 4 モデル、学習の不安定さ、reward hacking への対策が必要になる。
    • 直接選好最適化（DPO）は、採点器と強化学習を数式上で取り除き、選好ペアから言語モデルを直接更新する。実装は軽いが、固定データと更新後モデルの出力分布がずれる分布シフトがあり、PPO と DPO のどちらが常に優れるという合意はない。

    1. この講義の位置づけ ― LLM 学習の第 3 段階

    この節では、言語モデルを作る 3 段階を並べ、今回扱う第 3 段階が何を変え、何を変えないのかを説明する。 事前学習（pretraining）は言語の基礎を学ばせ、教師あり微調整（Supervised Fine-Tuning: SFT）は質問に答える型を教える。 その後の選好調整（preference tuning）は、答えの比較から得た人間の好みを使い、既にある能力の出し方、安全性、語調を整える。 このようにモデルの振る舞いを人間の意図や価値観へ合わせることを整合（alignment）という。

    画像の読み解き

    この図で重要なのは、3 つの段階が「何を教えるか」で明確に役割分担しているという点である。 pretraining（Lecture 4 の範囲）は膨大なテキストとコードから言語そのものの構造を学ぶ。極めて時間と計算資源を使う工程で、 終わった時点でモデルが直接学んだ仕事は「次の token を予測すること」だけである。token とは、モデルが文章を処理する文字列の小さな単位だ。 Afshine の言い方では 「素晴らしい autocompleter ではあるが、まだ helpful なモデルではない」。

    SFT は、その事前学習済みモデルを特定の仕事向けに仕上げる工程である。 ChatGPT のようなアシスタントに変えるのがその代表例で、規模ははるかに小さいが品質が非常に高いデータセットを使い、 「次にどの token を出すべきか」を正解例から教える。Lecture 4 で扱った LoRA（Low-Rank Adaptation、低ランク適応）は、更新するパラメータを少なくしてこの微調整を軽くする手法だった。

    そして今回の選好調整で教えるのは、新しい知識や新しい仕事ではなく、「同じ能力をどう見せると好ましいか」である。 Shervine が講義の終盤で言い切っているとおり、この段階の目的は 「新しい事実を学ばせることではない。既存の completion の分布に焦点を当て、モデルが返すべきものを人間が好むものに揃えること」だ。

    具体例。 SFT 済みのモデルは「振る舞い」としては正しくても、トーンが望ましくないことがある。 Afshine の例では「フレンドリーでない」「安全でない」といった側面が挙げられた。そういう軸を調整するのが第 3 段階である。

    2. Preference tuning とは何か ― teddy bear の例で掴む

    この節では、テディベアについての 2 つの答えを比べ、「好み」を学習可能なデータにする方法を説明する。 以後、質問を x、好まれた答えを yw（winner）、好まれなかった答えを yl（loser）と書く。講義が繰り返し使う質問 x は Suggest a new activity I could do with my teddy bear.（テディベアと一緒にできる新しい遊びを提案して）である。 SFT 済みモデル（LLMSFT）は、まず次のように答えた。

    I'd suggest you do not spend much time with your teddy bear at all.
    （テディベアと過ごす時間はあまり取らないほうがいいですよ。）

    文法上は自然でも、依頼を助ける答えにはなっていない。そこで、同じ質問に対して、より望ましい答えを用意する。

    Of course! Teddy bears not only make awesome companions for a delightful sleep, but can also be great buddies for fun activities. How about you both watch a movie together?
    （もちろん！ テディベアは心地よい眠りの相棒であるだけでなく、楽しい活動のよき仲間にもなります。一緒に映画を観るのはいかがでしょう？）

    この 「同じ質問に対する、好まれた答えと好まれなかった答えの組」 (x, yw, yl) が preference pair（選好ペア）である。 ラベルは「前者が 0.9 点」のような絶対点ではなく、yw ≻ yl、つまり「前者を後者より好む」という相対関係だ。 スライドの言葉では 「Context. Model may misbehave. Need to inject negative signals.（モデルは望ましくない振る舞いをしうる。負のシグナルを注入する必要がある）」。

    周辺情報：この「負のシグナル」という言い方が本質。 通常の SFT の損失は、与えられた正解列の確率を上げるように作られているため、データに悪い答えを置いて 「これは出すな」と直接指定する欄がない。 Afshine もこう述べている ― 「SFT はモデルに何を予測すべきかを教えるが、何を予測すべきでないかは教えない」。 preference tuning は損失関数に「負けた応答」を明示的に組み込むことで、この欠落を埋める。 後述する reward model は選好ペアから「プロンプト＋応答」を 1 個の好ましさスコアへ写す採点器で RL や BoN に再利用でき、 DPO（Direct Preference Optimization）は別の採点器を作らず、policy と固定 reference の尤度比をペアで直接学習する。 どちらの損失も （勝った側） − （負けた側） という差分の形をしているのはそのためである。

    3. なぜ SFT だけで済まないのか ― 3 つの理由

    この節では、SFT だけで好ましい振る舞いを作り切りにくい理由を、①正解文を一から書く難しさ、②データ分布への敏感さ、 ③高品質データを増やす費用、の順に説明する。ただし、選好調整は壊れた SFT を隠す万能薬ではなく、 モデルの大きな不調は SFT データを見直す合図でもある、という講義の注意も残す。

    理由 1：比較は生成よりはるかに簡単

    Afshine の説明はこうだ ― 「『素晴らしい詩をゼロから書け』と言われるのと、『悪い詩と良い詩を 2 つ見せるのでどちらが良いか言え』と言われるのでは、後者のほうが圧倒的に簡単」。 SFT のデータを作るには「理想の応答」そのものを人間が書かなければならないが、選好データなら 2 つ見て選ぶだけで済む。 このため、比較によるラベル付けは、理想文を執筆するより速く、評価者間の基準も合わせやすい。

    理由 2：SFT ではプロンプトの分布が極めて重要で、壊しやすい

    SFT データセットを作るとき、実務家が最も神経を使うのが プロンプトの分布 である。 特定タイプのプロンプトが多すぎると、モデルはその方向に偏った応答をするようになる。 ここでいう分布とは、どの種類の質問がどの割合で含まれるか、というデータ全体の構成である。 「モデルが 1 件おかしな挙動をしたから SFT データに 1 件足そう」としても、 その追加がモデル全体をどちらへ偏らせるかを慎重に見極めなければならない。 選好調整にもデータ分布は重要だが、講義の主張は、SFT の正解例を継ぎ足す場合ほど直接的に出力分布を壊しにくい、という相対的な違いである。

    理由 3：SFT データの品質確保はスケールしない

    SFT データは非常に高品質でなければならない。モデルのあらゆる失敗を拾って SFT データに落とし込もうとすると、 時間がかかりすぎて回らなくなる。「ただ大変なだけになる」と Afshine は言う。

    講義で明示された重要な但し書き。 「preference tuning はすべての答えではない。モデルが盛大に misbehave しているなら、それは SFT データセット自体に問題がある可能性もある。 そういうときは preference tuning に走る前に SFT データを点検したほうがよいこともある」。 スライド最下部の一文（“However, "model misbehaving" can also be a good wake-up call to check SFT data quality”）はこれを指している。

    周辺情報：LoRA との関係（受講生の質問より）。 「SFT には LoRA があったが、preference tuning における LoRA 相当は何か？」という質問に対する Afshine の整理が明快だった。 LoRA は「チューニングするパラメータ数を減らす方法」、preference tuning は「目的関数（損失）が違う話」であり、両者は直交する概念。 つまり DPO を LoRA で回す、といった組み合わせは普通に可能で、両者は互いに排他ではない。 実際 Hugging Face TRL の DPOTrainer は PEFT（LoRA など）と併用する構成を公式にサポートしている。

    4. 選好データの 3 形式 ― pointwise / pairwise / listwise

    この節では、質問と答えの 1 組 (x, ŷ) に好ましさを付ける 3 方式を比べる。 x は質問、ŷ はモデルが生成した答え、Observation = (x, ŷ) は評価対象 1 件を表す。 1 件ずつ点数を付ける pointwise（個別評価）、2 件を比べる pairwise（ペア比較）、 複数件を並べ替える listwise（リスト順位付け）のうち、人間が判断しやすく学習にもつなげやすい pairwise が中心になる。

    形式ラベルの付け方人間にとっての難易度講義の評価
    Pointwise 1 件ごとに絶対スコア（例: 0.9） 最も難しい 「これは 0.9、これは 0.2、とスケールをどう決めるのかが全く明確でない」
    Pairwise 2 件を並べてどちらが良いかを指定 最も易しい 実務で標準的に使われる。以降の講義もこれで進む
    Listwise n 件をまとめて順位付け 中間 「どれだけ良いか」を言わなくてよい分 pointwise より楽だが、なお少し複雑

    周辺情報：なぜ絶対評価が難しいのか。 絶対スコア付けは、評価者ごとに点数の基準がずれるうえ、同じ評価者でも直前に見た事例によって基準が動く。 相対比較はこの「基準のドリフト」に強い。これは情報検索の learning-to-rank 分野で古くから知られる pointwise / pairwise / listwise の分類とまったく同じ整理で、 LLM の選好データ収集にもそのまま持ち込まれている。 なお実運用の選好データセット（例: Hugging Face TRL が例示に使う UltraFeedback や、 Chatbot Arena 由来の lmarena-ai/arena-human-preference-55k）も、いずれも chosen / rejected の ペア形式で配布されている。

    5. ペア選好データの作り方 ― 2 ステップのレシピ

    この節では、選好ペアを作る実務を「候補を作る」「どちらがよいか決める」の 2 段階で説明する。 先に実際の利用に近い質問を集め、同じ質問から複数の答えを作る。次に、明確な評価基準を人間または代理の採点方法へ渡し、 (x, yw, yl)へ整える。このデータが、次節以降の reward model と DPO の共通の出発点になる。

    ステップ 1：同じプロンプトに対して応答を 2 つ生成する

    • 入力（質問 x）：実際の利用者が尋ねる内容に近づけるため、運用ログ、または意図的に設計した質問の分布から取る。個人情報や機密情報を扱う場合は、収集前の保護設計が別途必要になる。
    • 出力（候補回答 ŷ）：同じ質問を、temperature T > 0 にした SFT モデルへ複数回入れる。temperature は生成のばらつきを調整する値で、0 より大きくすると同じ質問から違う候補を得やすい。ほかに合成データや rewrite（人手での書き直し）も使える。

    rewrite とは、ログの中から「気に入らなかった応答」を見つけ、それを人手で良い応答に書き直すやり方。 まさに §2 の teddy bear の例がこれである。ただし Afshine は 「生成が必要な分、少し手間が増える」と注記している ― §3 で述べた「比較のほうが生成より楽」という原則の裏返しだ。

    ステップ 2：2 つの応答にラベルを付ける

    • 人間による比較：評価者が 2 つを読み、基準に沿って一方を選ぶ。RLHF の Human Feedback はこのラベルの由来を指す。
    • LLM-as-a-judge：評価基準と候補を別の大規模言語モデル（Large Language Model: LLM）へ渡し、比較判定を任せる。大量処理しやすく意味や指示遵守も見られるが、判定モデルの偏り、位置順への偏り、自己モデルを好む偏りを引き継ぎうる。
    • 古典的な自動指標：BLEU（Bilingual Evaluation Understudy）や ROUGE（Recall-Oriented Understudy for Gisting Evaluation）で参照文との表面上の重なりを測る。講義では、自由な対話の好ましさには最近あまり使われないと説明された。
    • 判定の細かさ：最も単純なのは「A と B のどちらがよいか」だけの 2 値判定。much better から much worse まで段階を付けることもできるが、主観的な課題では境界を揃えにくいため、講義では 2 値が多いとされた。

    周辺情報：BLEU と ROUGE とは何か。 BLEU と ROUGE は、いずれも生成文と参照文の n-gram の重なりで自動採点する古典的指標。人手を使わず大量の候補を一貫して採点するために導入され、 BLEU は機械翻訳向けで適合率（precision）寄り、ROUGE は要約向けで再現率（recall）寄りという違いがある。 参照文との表層一致しか見ないため、意味は同じでも言い回しが違う応答を低く評価してしまう。 オープンエンドなチャット応答の「好ましさ」を測るには不向きで、講義が「最近はあまり使われない」と言うのはこの理由による。 代わりに主流になったのが LLM-as-a-judge（強力な LLM に 2 応答を比較採点させる）である。

    講義で強調された落とし穴：ガイドラインの質。 Afshine は「人間の評価は、提示するガイドラインに非常に敏感だ」と釘を刺している。 「ガイドラインをできるだけ客観的にすることが重要。完全に客観的にはできないこともあるが、少なくとも十分に明確にしておかないと、 人間の選好データがノイズだらけになる」。選好データの品質は、モデルではなく評価設計で決まる部分が大きい。

    6. 強化学習（RL）の基礎 ― LLM に写像して理解する

    この節では、強化学習（Reinforcement Learning: RL）の基本語を、言語モデルが 1 token ずつ文章を作る場面へ対応付ける。 ここでの方策（policy）は「現在の文脈から次の token を選ぶ確率分布」であり、学習対象の言語モデルそのものだ。 完成した答えへの評価を使い、良かった生成を起こしやすくするのが、後段の RLHF（Reinforcement Learning from Human Feedback、人間のフィードバックからの強化学習）である。

    標準的な RL の枠組み

    • agent（行動主体）が environment（環境）とやり取りする。
    • 時点 t の state（状態）st を見て、action（行動）at を選ぶ。
    • 選び方は policy（方策） πθ(at | st) で表す。π は確率分布、θ は学習するモデルの重み、縦線 | は「状態 st が与えられたとき」を意味する。
    • 行動の結果を reward（報酬）という数値で評価し、将来の報酬が大きくなるよう θ を更新する。

    7. RLHF の全体像 ― 2 つのステップ

    この節では、ここまで集めた選好ペアが、どのように言語モデルの更新へ届くかを 2 段階でつなぐ。 第 1 段階では、質問と答えから好ましさを 1 個の数値へ変えるreward model（報酬モデル）を学ぶ。 第 2 段階では、その採点器を固定したまま、現在の言語モデルが作った答えを採点し、policy を更新する。 つまり流れは、データ収集 → reward の学習 → RL による生成分布の改善である。

    Step 1 — Reward modeling

    集めた選好ペアを使い、「良い出力」と「悪い出力」を見分けるモデルを学習する。入力はプロンプトと応答の連結、出力はスコア 1 つ。

    policySFT モデルを初期値として用意更新好ましい答えを出す確率分布そのものを変えるため
    reference policySFT モデルの複製を用意凍結元の能力から離れすぎていないか測る基準にするため。詳しくは §11

    Step 2 — Reinforcement learning

    その reward を使い、LLM（policy）を選好に整合するよう更新する。入力はプロンプト、出力は reward の高い応答。

    "HF" が指しているもの。 Afshine が明示的に注意を促した点 ― 「RLHF の Human Feedback の部分は、reward model を訓練するラベルを指している。 選好ペアが人間の評価に基づくなら人間の選好に依拠していることになり、RLHF である」。 逆にラベルが人間由来でない場合は RLAIF（Reinforcement Learning from AI Feedback）と呼ばれる、と講義でも言及があった。

    周辺情報：RLAIF の代表例。 人間ラベルの代わりに AI がフィードバックを与える方式として広く知られるのが Anthropic の Constitutional AI で、 あらかじめ定めた原則（"constitution"）に照らして AI 自身が応答を批評・修正し、その選好ラベルで学習する。 人間アノテーションのコストとスケール制約を外せる一方、フィードバックを与えるモデルの偏りがそのまま継承されるというトレードオフがある。 RLHF / RLAIF のどちらであっても、以降の Step 1・Step 2 の数式的な枠組みはまったく同じである。

    8. Step 1：reward model と Bradley-Terry 定式化

    この節では、2 つの答えの比較結果から、1 つの答えを単独で採点できる reward model を学ぶ考え方を説明する。 使うのは Bradley-Terry pairwise model（Bradley-Terry ペア比較モデル）である。 reward model を r(x, y) と書き、質問 x と答え yを入れると、好ましさを表す実数が 1 つ返るとする。 同じ文でも質問によって良し悪しが変わるため、答えだけでなく質問も必ず入力する。

    では、そんなモデルをどう学習するのか。ここで登場するのが Bradley-Terry 定式化 である。 Afshine は 「これは重要な式なので、少しここに留まります」と言って時間をかけた。

    p(yi > yj) = eri / ( eri + erj ) = σ( ri − rj ) p は「答え y_i が y_j より好まれる確率」。r_i = r(x,y_i)、r_j = r(x,y_j)。e は自然対数の底、σ は sigmoid 関数 σ(z)=1/(1+e^{-z})

    この式が言っていること

    右辺の変形（= σ(ri − rj)）を見ると、直感が一気に働く。sigmoid は 入力が −∞ で 0、+∞ で 1 に漸近する S 字カーブである。したがって、

    • yi が yj より良いなら、確率を 1 に近づけたい → ri − rj をできるだけ大きくしたい。
    • つまり 良い出力の r は高く、悪い出力の r は低くなるようモデルを学習すればよい。

    数字で確かめる。ri=2、rj=1なら差は 1 で、 σ(1)≈0.73、つまり yi が選ばれる確率は約 73% と表される。 両方へ 10 を足して 12 と 11 にしても差は 1 のままなので確率は変わらない。 reward の絶対値ではなく差だけが識別できるのが、この定式化の核心である。

    周辺情報：Bradley-Terry モデルの出自。 スライドの脚注にあるとおり原典は 1952 年の統計学論文 “The rank analysis of incomplete block designs: I. the method of paired comparisons”（Bradley & Terry）。 LLM のために作られた式ではなく、「対戦・ペア比較の結果から各個体の強さを推定する」ための 70 年以上前の古典モデルである。 各個体に潜在的な強さ r を割り当て、勝敗確率をその差の logistic 関数で表す ― チェスの Elo レーティングと同系統の発想だ。 Hugging Face TRL の RewardTrainer 公式ドキュメントも、reward model の損失を p(y⁺ ≻ y⁻ | x) = σ(r(x, y⁺) − r(x, y⁻)) という Bradley-Terry の形で明示しており、 講義の式がそのまま現代の実装に載っていることが確認できる。

    周辺情報：sigmoid（logistic 関数）の基本。 σ(x) = 1 / (1 + e−x)。実数全体を (0, 1) に押し込むので確率として解釈できる。 σ(0) = 0.5、σ(−x) = 1 − σ(x)（原点対称）という性質があり、 Bradley-Terry では「差が 0 なら勝敗五分五分」という自然な意味に対応する。 また σ'(x) = σ(x)(1 − σ(x)) と微分が簡潔なため、勾配計算にも都合がよい。 なお 2 択なので softmax の 2 クラス版がちょうど sigmoid に一致する ― 講義中、受講生から「この σ は softmax ではないのか」という質問が出たが、 Afshine は「reward model はペアで学習しているので σ（ペアワイズ）だ」と整理している。

    9. reward model の損失関数を第一原理から導出する

    この節では、Bradley-Terry の選好確率を、学習プログラムが最小化できる損失へ変える。 観測された選好ペアが起きる確率を最大にする最尤推定（Maximum Likelihood Estimation: MLE）から始め、 積を和へ変える対数を取り、最後に符号を反転して負の対数尤度（Negative Log-Likelihood: NLL）を得る。 この順を追うと、式を暗記せず、二値交差エントロピーと同じ形になる理由を理解できる。

    導出の 5 ステップ

    1. データを置く。 i=1,…,n 番目のデータを (xi, yw,i, yl,i) とする。n はペア数、添字 w は好まれた答え、l は好まれなかった答えで、各ペアは独立と仮定する。
    2. MLE で尤度を最大化する。 reward model の重みを φ と書くと、観測された全勝敗の同時確率は独立性により積になる： maxφ Πi=1..n Pφ(yw,i ≻ yl,i | xi)。
    3. Bradley-Terry を代入する。 各確率を σ(rφ(xi,yw,i) − rφ(xi,yl,i)) に置き換える。
    4. log を取る。 Afshine の助言 ― 「確率の積を見たら、まず考えるべきは log。積は非常に小さくなり得て数値的な不安定さを招くから」。積の最大化は log の最大化と同値なので、Σ log σ(·) になる。
    5. 符号を反転して NLL にする。 「ML の人間は最小化が好きなので、頭にマイナスを付ける」。対数尤度の最大化を負の対数尤度の最小化へ変換し、最適化器で扱える損失関数が完成する。
    𝓛RM(φ) = − 𝔼(x,yw,yl)∼𝒟 [ log σ( rφ(x,yw) − rφ(x,yl) ) ] 𝒟 は選好データセット、𝔼 はデータ全体の平均、φ は reward model の重み。実装では期待値をミニバッチ平均で近似する

    1 ペアだけで、reward の差が 0 なら予測確率は 0.5、損失は −log 0.5≈0.693 である。 差を 2 まで広げると確率は σ(2)≈0.881、損失は約 0.127 まで下がる。 つまり最小化すると、好まれた答えの score を負けた答えより高くする方向へ学習が進む。

    この講義でいちばん美しい問い

    導出後、Afshine が受講生に投げた質問が秀逸だった ― 「損失関数はペアワイズだ。では reward model 自体はペアワイズか、ポイントワイズか？」

    教室からは「ペアワイズ」という答えが返ってきたが、正解は ポイントワイズ である。

    そこが美しいところで、ペアは必要ないんです。学習はペアワイズにやるけれど、出来上がるのはポイントワイズなモデル。 最終的には、1 つのプロンプトと 1 つの出力を受け取って、数値を 1 つ返す reward model が手に入る。

    学習時だけペアで縛り、推論時は 1 件ずつスコアリングできる ― この性質があるからこそ、後述する Best-of-N（N 個の候補を独立に採点して最良を選ぶ）が成立する。

    周辺情報：これは「最尤推定（MLE）→ 負の対数尤度（NLL）」という王道の型。 この 5 ステップは reward model 固有のものではなく、統計・機械学習で最も標準的な損失関数の作り方そのものである。 「データの生成モデルを仮定 → 尤度を書く → 対数を取る → 符号を反転して損失にする」。 Bradley-Terry の確率は 2 値なので、出来上がる損失は binary cross-entropy の特殊形になる （受講生の最初の答えは正しかった）。Afshine 自身も 「cross entropy はこれの特殊ケースと見なせる」と応じている。

    11. Step 2：RL で LLM を整合させる ― と reward hacking

    この節では、固定した reward model の点数を高めながら、SFT モデルが元から持つ能力を壊さないよう policy を更新する方法を説明する。 学習中に重みを変えないことを凍結（frozen）といい、reward model と基準用の reference policy は凍結し、現在の policy πθだけを更新する。 点数だけを追うと、既習能力を失う破滅的忘却（catastrophic forgetting）や、採点器の弱点を突く reward hackingが起こる。そこで、reward と「基準から離れすぎない」という制約を同時に最適化する。

    目的関数は 2 項からなる

    スライドの一文が目的関数の全体像を要約している ― 「Objective function optimizes for higher rewards without going too far from the base model（reward を最大化するが、ベースモデルから離れすぎない）」。

    Afshine は「前半は誰でも納得するはず。では、なぜ後半が必要なのか？」と教室に問いかけ、3 つの理由を引き出した。

    J(θ) = 𝔼x∼𝒟, y∼πθ(·|x)[ rφ(x,y) ] − β DKL( πθ(·|x) ‖ πref(·|x) ) 模式的な KL 正則化 RLHF 目的。𝒟 は質問の分布、y は生成した答え、β>0 は基準からの逸脱を罰する強さ。J は最大化する

    第 1 項だけなら reward model の点数を上げるほどよい。第 2 項は現在の policy と reference policy の違いを罰する。 β を大きくすると元の SFT モデルを強く守り、小さくすると reward を追って大きく変わりやすい。 実際の PPO 実装では token ごとの log 確率比を使ってこの制約を近似・加算する。

    ① 破滅的忘却（catastrophic forgetting）

    pretraining と SFT で獲得した膨大な知識が、RL で引き離されると失われてしまう。受講生の最初の回答で、Afshine は「まさにそれ」と全面同意した。

    ② reward hacking

    reward model は不完全なので、その不完全な指標に過剰最適化すると、reward は上がるが本来の目的は達成されない。

    ③ 学習の不安定性

    更新が大きすぎると学習が発散する。RL は元来不安定になりやすい。

    reward hacking ― 講義中いちばん記憶に残る例え

    Afshine が自分自身を題材にして説明した例が秀逸だった。

    私が講義をしているとしましょう。目的は「できるだけ情報量の多い講義にすること」です。 そこで、それを定量化するために 「講義の最後の拍手の大きさ」を reward に選んだとする。 問題は、拍手の音量に過剰最適化すると起きる。皆さんがジョークを好きだと分かったので、ジョークばかり言い始める。 すると最後に拍手が起きて reward は最大化される。けれど本来の目的 ―「情報量の多い講義」― は達成されていない。

    reward hacking とは、不完全な指標に過剰最適化してしまい、reward は最大化されるのに本来の目的は満たされない現象である。 受講生の言葉を借りれば「きれいでないデータに overfit してしまう」ことでもあり、Afshine は両者は同じ話だと整理した。

    周辺情報：これは古典的な Goodhart の法則。 「測定基準が目標になると、それは良い測定基準でなくなる（When a measure becomes a target, it ceases to be a good measure）」。 AI 安全性の文脈では specification gaming（仕様の抜け穴を突く挙動）とも呼ばれ、 「掃除ロボットがゴミを見つけないように目を閉じる」といった事例が有名である。 LLM の RLHF で実際に観測される reward hacking の典型は 冗長性バイアス（長く書くほど reward model が高評価しやすい）や 過剰な追従（sycophancy：ユーザーに同調しすぎる）で、 いずれも「reward model が学習データから拾った偏りを policy が突く」形で現れる。 後述の KL ペナルティは、この暴走に対する最も基本的な歯止めという位置づけになる。

    Kullback-Leibler（KL）divergence ― 「離れすぎない」を数式にする

    2 つの確率分布の違いを測るのが Kullback-Leibler divergence（KL ダイバージェンス、KL 乖離度）である。 Afshine は 「皆さんが知っている前提にはしたくない」と言って定義から始めた。

    DKL( P ‖ Q ) = Σi pi log( pi / qi ) P=(p_i) と Q=(q_i) は同じ候補 i 上の確率分布。log は自然対数。P の下で平均した log 確率比で、単位は nat

    小さな例として、reference が 2 語へ Q=(0.5,0.5)、現在の policy が P=(0.75,0.25) を割り当てたとする。すると DKL(P‖Q)=0.75 log(1.5)+0.25 log(0.5)≈0.131 である。 同じ分布なら 0、違いが大きいほど値は大きくなる。ただし Afshine は 「距離とは呼びたくない」と強調した。向きを入れ替えると一般に値が変わり、三角不等式も満たさないからである。

    さらに教室に「KL divergence は正か負か？」と問い、正（非負）であることを引き出したうえで、「なぜ？」と踏み込んだ。 答えは Jensen の不等式。式の中の log は正にも負にもなり得るので一見自明ではないが、Jensen の不等式で常に 0 以上であることが示せる。 そして KL = 0 となるのは P と Q が等しいとき、かつそのときに限る。

    周辺情報：なぜ「距離ではない」のか。 KL divergence は非対称（KL(P‖Q) ≠ KL(Q‖P)）であり、三角不等式も満たさない。 数学的な意味での距離（距離空間の公理）を満たさないので、正確には「ダイバージェンス（乖離度）」と呼ぶ。 実装上も向きの選択は重要で、Hugging Face TRL の PPOTrainer は学習中の指標として objective/kl（現在の policy と reference policy の平均 KL）を記録し、 objective/non_score_reward = beta * kl、objective/rlhf_reward = score − non_score_reward という形で reward から KL ペナルティを差し引いた値を最終的な最適化対象として追跡している。 講義の目的関数がそのまま実装のログ項目になっている、と見ると分かりやすい。

    式の向きに関する一次資料上の注意。 §13 の講義スライドは KL 項を KL[πref,πθ] の順で表示しており、図の説明はその表記を忠実に残している。 一方、DPO 原論文が出発点にする標準的な KL 正則化目的と多くの RLHF 実装は DKL(πθ‖πref)、すなわち現在の policy から reference への向きを用いる。 KL は非対称なので同一視できない。本節の数式は後者を採用し、講義スライドの転記と実務上の標準を区別した。

    12. reward ではなく advantage を最大化する ― value function と GAE

    この節では、完成した答えに 1 個だけ付く reward を、各 token の更新へどう結び付けるかを説明する。 絶対点ではなく「その時点で期待した点より、実際はどれだけ良かったか」を表す advantage（優位度）を使う。その期待値を出すのが value function（価値関数）であり、 advantage を安定して推定する代表的方法が GAE（Generalized Advantage Estimation、一般化アドバンテージ推定）である。 これらは次節の PPO（Proximal Policy Optimization、近接方策最適化）を読むための準備になる。

    13. PPO ― Proximal Policy Optimization

    この節では、policy gradient を一度に動かしすぎない PPO（Proximal Policy Optimization、近接方策最適化）を説明する。 PPO-Clip は直前の policy と比べた確率の変化を切り詰め、PPO-KL Penalty は固定した reference からの乖離へ罰則を課す。 前者は一回ごとの更新、後者は学習開始点からの累積的な変化を抑える、と分けると読みやすい。 Afshine は 「proximal（近接）なのは、離れすぎたくないから」と説明した。

    policy ratio（方策比） rt(θ) = πθ(at|st) / πθold(at|st) は、 現在の policy が、rollout を作った直前の old policy より、その token を何倍出しやすくしたかを測る。 πθold は PPO の更新を数エポック回す間は固定する。比が 1 なら確率は変わっていない。 clipping はこの比を [1−ε, 1+ε] に切り詰め、epsilon（ε）で許容更新幅を決める仕組みである。 advantage が示す方向へは進みつつ、一度の過大更新で policy が壊れるのを防ぐため導入される。

    複雑に見える式も、advantage の符号で場合分けすると読める。たとえば ε=0.2 なら許容帯は [0.8,1.2]。良い生成の確率比が 1.4 まで上がっても、目的上の改善は 1.2 で頭打ちになる。 悪い生成の比を 0.6 まで下げても、0.8 より先へ下げる追加利益を与えない。 ただし clip するのは目的関数の中の比であり、モデルの実際の確率を範囲内へ投影する硬い制約ではない。 そのため実装では KL や clip された割合も監視する。

    変種 2：PPO-KL Penalty

    PPO-KL Penalty は、PPO の目的に Kullback-Leibler divergence の罰則を加える変種である。 old policy との局所的な更新幅だけでなく、固定した reference policy（通常は SFT 済みベースモデル）からの累積的な逸脱も抑え、 reward hacking や破滅的忘却を防ぐために使う。

    こちらは「比 × advantage」から KL divergence を β 倍して引く。 β>0 は reference へ戻す力の強さである。PPO 原論文では clip と KL penalty は別の変種として提示されたが、 LLM の RLHF 実装では、old policy に対する clipping と reference policy に対する KL penalty を併用することが多い。

    用語の整理（スライドに明記）。

    • old = 前回の RL イテレーションのモデル
    • ref = ベースモデル（SFT モデル）

    そして Shervine・Afshine 双方が強調したのは、2017 年の PPO 原論文の KL penalty は old に対する近接制約として導入されたが、 2025 年の LLM 文脈では、元の能力を守る目的で ref（SFT モデル）に対する KL penalty を加えるのが普通という点。 「この論文は 2017 年に出て、LLM は 2020 年代に普及したものなので、そこに入れるものが変わってきた」。

    さらに実務上の注記として ― 「最近 PPO で policy を学習する人は、たいてい KL divergence を使い、それを old イテレーションを使う clipping と混ぜることもある。 損失の定式化には多くのバリエーションがあり、私が言ったことが常に正しいわけではない」。 つまり 実装は「clip か KL か」ではなく「clip も KL も」が現実ということである。

    周辺情報：PPO の系譜と実装のデフォルト値。 PPO は同じ Schulman らの TRPO（Trust Region Policy Optimization）の後継で、 原論文（arXiv:1707.06347）は「TRPO の利点を持ちつつ、実装がはるかに単純で汎用的、経験的にサンプル効率も良い」と位置づけている。 「1 サンプルにつき 1 回の勾配更新」しかできない従来の policy gradient に対し、 同じデータで複数エポックのミニバッチ更新を回せるようにしたのが PPO の実務的な貢献である。 なお clip の範囲 ε は実装上 0.2 が事実上の標準で、Hugging Face TRL の PPOTrainer も --cliprange 0.2 を既定とし、「val/ratio は 1.0 付近を漂うはず。2.0 や 0.1 のように極端なら、連続する policy 間の更新が急すぎる」という デバッグの目安を公式ドキュメントに明記している。講義の rt(θ) がそのまま監視指標になっているわけだ。

    15. RL ベース手法の 6 つの課題

    この節では、PPO ベース RLHF を実際に運用すると現れる 6 つの難しさを整理する。 reward model との二段構え、多数の調整値、学習の不安定さ、監視の難しさ、出力の探索、そして「そもそも RL が必須か」である。 最後に、現在の policy が自分で作ったデータを使う on-policy と、別の生成元による固定データを使う off-policy を区別し、この疑問が Best-of-N と DPO へつながることを示す。

    3学習の不安定性 イテレーションの幅を制約してもそれだけでは足りないことがある。
    4監視すべき指標がない 平均 reward や KL は監視できる。しかし pretraining や SFT の交差エントロピー損失のように、人間が本当に望む振る舞いをどれだけ再現できたかを直接保証する値ではない。reward hacking があれば平均 reward だけ上がることもある。
    5completion の多様性（exploration）が必要 RL の学習ループで毎回似た出力しか生成しないと、可能な completion 空間を探索できていない。何が良いかを知るには、モデルに探索を強制する必要がある。
    6そもそも RL が必須なのか不明瞭 スライドの表現は “Not abundantly clear why preference tuning absolutely needs RL”。Afshine 自身 「私も RL に馴染みがなかったし、この段階になぜ RL が必要なのか、そこまで明白ではない」と率直に述べた。

    on-policy と off-policy

    on-policy は学習中の policy 自身がいま生成したデータでその policy を更新する方式、 off-policy は別の policy や人間が過去に作った固定データでも学ぶ方式である。 前者は現在の生成分布を直接改善できる一方、毎回 rollout（質問から最後まで生成した回答）が必要で高コストになる。 後者はデータを再利用しやすい一方、今のモデルが実際に出す答えとのずれに注意が要る。

    on-policyoff-policy
    定義学習中のモデルが現在の policy から生成し、それに対して最適化する学習対象のモデルが生成したものではないデータに依拠する
    該当例PPO は基本的に on-policy。old policy の rollout を短期間だけ複数回使う古典的な例は replay buffer に蓄えた過去データから学ぶ RL。SFT や DPO は固定データを使うという広い意味でこちら側
    この講義での意味各イテレーションで現在に近いモデルから回答を作り、その評価で更新する収集済みの正解例・選好ペアを再利用する

    用語上の注意。 DPO は固定の選好データを使うため「offline preference optimization」と呼べるが、reward と環境遷移を使う通常の off-policy RL アルゴリズムではない。 本レポートで「off-policy 側」と書くときは、学習中の policy が今生成した rollout ではないデータを使うという広いデータ由来の意味である。

    「SFT では、こちらが用意したプロンプトと応答をモデルに真似させていた。だがここでは、各イテレーションでモデル自身に出力を生成させ、 その出力の良さを使ってモデルを更新する。ここに本質的な違いがある」。

    「なぜ選好データで SFT をしないのか？」という受講生の質問に対する Afshine の答えは、§2 の議論に戻る ― 「SFT は『この入力にはこれを生成せよ』と教えるだけで、生成すべきでないものについては何も教えない。 起きてほしくない出力があっても、それを完璧な文に書き直さない限り、伝統的な SFT の枠組みでは『それを生成するな』と伝える方法がない」。 そのうえで 「素晴らしい振りです。10 分後に、RL でやったことを教師ありでやる方法を見ます」と DPO を予告した。

    ここまでで選択肢は二つに分かれる。reward model は便利な採点器なので残し、policy 学習だけを省くのが次節の Best-of-N。 一方、reward model と RL の両方を数式で取り除き、選好ペアから直接 policy を学ぶのが §17 以降の DPO である。

    16. Best-of-N（BoN）― RL をやらずに reward model だけ使う

    この節では、policy を一度も更新せず、既に学んだ reward model を推論時の選別器として使う Best-of-N（BoN）を説明する。同じ質問から N 本を生成し、各回答を独立に採点して最大 score の 1 本だけを返す。 RL の不安定さは避けられるが、仕事を推論時の計算量と待ち時間へ移す方法である。

    戦略（スライドより）。

    1. プロンプトを与え、SFT モデルで複数の出力を生成する（SFT モデルは学習しない。そのまま使う）。
    2. 各出力を reward model のスコアでランク付けする。
    3. 最良のものを返す。
    y* = arg maxy1,…,yN ∼ πSFT(·|x) rφ(x,yi) x は質問、y_i は SFT policy から生成した第 i 候補、r_φ は凍結した reward model、arg max は score を最大にする候補そのものを選ぶ操作

    ここでは N=3 で、score は 0.8、−2、0.2。最大は 0.8 なので、その回答だけを返す。 score が負でも問題はなく、絶対的な 0 の意味も不要である。 §9 で確認した「reward model はポイントワイズ」という性質が、ここで実際に効いている。

    BoN の弱点 ― 学習コストを推論コストに付け替えただけ

    Afshine は「この方法の問題は何か？」と教室に問い、2 つの答えを引き出した。

    • モデル自体が悪ければ結果も悪い。 ただし十分な数を十分高い temperature で生成すれば多様性は確保できるので、ある程度は緩和できる。「全部の応答が悪かったら？」という追い打ちの質問には 「これは確かに懸念。モデルは最低限それなりに良くないといけない」と認めている。
    • 推論時に何度もモデルを叩く。 これが本命の問題。「RL の学習はスキップできるが、その仕事を全部推論段階に押し付けている。すべてが極めて高コストになる」。

    だから Afshine は実務的な助言をする ― 「この道を選ぶ前に、推論トラフィックの見積もりと学習コストを比べて判断するとよい」。 大量のトラフィックを捌く必要がある場合、コストの観点から BoN は成立しないことがある。

    Shervine の追撃：「無限の予算があっても解決しない」

    DPO パートを引き継いだ Shervine は、BoN の弱点をもう一段深く掘り下げた。

    思考実験として、無限のお金があったらどうでしょう。全部を並列に生成するとしても、 結果を返すには「最も遅い 1 本の生成が終わるまで」待たねばならない。 レイテンシの分布を見ると、たいてい 1 点に集中した形ではない。そして N 個の答えの最大値の確率分布は、右にシフトする。 つまり無限の金と計算資源があっても、1 回のパスより待たされる。

    各生成時間にばらつきがあり、全候補の終了を待つ設計なら、N 本の最大待ち時間は通常 1 本の待ち時間より長くなる。 これは コストだけでなくレイテンシの構造的な問題で、並列計算へ資金を投じても完全には消えない。BoN が万能薬になれない理由である。

    周辺情報：スケールに関する Q&A の要点。 「reward のスケールに制約はあるか」という質問に Afshine はこう答えた ― 「BoN では最大値を取るだけなのでスケールは気にしなくてよい。正規化しても最大のものは最大のままだから。 だがスケールが効くのは、それが損失関数に入るとき ― つまり RL の場合。だからそこでスケーリング機構を使う」。 単調変換で順位が保たれるかどうかが分水嶺、という整理である。

    17. DPO ― Direct Preference Optimization

    この節では、DPO（Direct Preference Optimization、直接選好最適化）が 「好ましい答えを増やし、好ましくない答えを減らす」更新を、通常の分類損失として行う仕組みを説明する。 明示的な reward model、value model、on-policy rollout を使わず、学習する policy と凍結した reference policy の 2 つだけで、 選好ペアを直接処理する。PPO の 4 モデル問題と BoN の推論負荷を同時に避けるのが動機である。

    不満 1：モデルの重みを 4 つ抱える

    損失最適化の間じゅう、現在の policy、old / reference の policy、advantage が隠し持つ reward model、そして value function を保持し続けねばならない。

    不満 2：BoN はレイテンシとコストが痛い

    しかも無限の予算でも最大値のレイテンシ分布は右にシフトするため、単一パスより必ず遅くなる。

    だから：教師ありでやれないか？

    「なぜずっと教師ありでやらないのか」という受講生の問いこそ、DPO の著者たちが探究した道だった。

    𝓛DPO(πθ; πref) = − 𝔼(x, yw, yl) [ log σ( β log (πθ(yw|x) / πref(yw|x)) − β log (πθ(yl|x) / πref(yl|x)) ) ] (x,y_w,y_l)∼𝒟 は選好ペア、π_θ は学習する policy、π_ref は凍結した基準、σ は sigmoid、β>0 は KL 正則化と対応する尺度。明示的な reward 関数は現れない

    π(y|x) は、質問 x の後に回答列 y=(y1,…,yT) 全体を生成する確率であり、 各 token の条件付き確率の積である。実装では積のまま扱うと極端に小さくなるので、 log π(y|x)=Σt log π(yt|x,y<t) と log 確率を足す。 DPO は「policy が reference より chosen をどれだけ押し上げたか」と 「rejected をどれだけ押し上げたか」の差を正にしようとする。

    この式の何がすごいのか

    Shervine の解説を追う。

    • 独立した reward model がない。 「見てのとおり、もう r がない」。ただし reward の考え自体は、policy と reference の log 比として暗黙に残る。
    • 選好ペアを分類できる。 括弧の中は、chosen と rejected のreference に対する正規化 log 尤度の差である。これを大きくすると、chosen を選ぶ予測確率が 1 に近づく。
    • Bradley-Terry の姿がそのまま見える。 「よく見ると、Afshin が説明した Bradley-Terry 定式化が見えてくる。log σ の期待値があり、σ の中に差分がある。そしてその差分に、reward 相当の項が見える」。

    小さな例を置く。reference が chosen と rejected にともに 0.10 を与え、更新中の policy がそれぞれ 0.20 と 0.05 を与えたとする。正規化 log 尤度は log(0.20/0.10)=log 2 と log(0.05/0.10)=log 0.5 なので、その差は log 4≈1.386。β=1 なら選好確率は σ(1.386)=0.8 となり、このペアの損失は −log 0.8≈0.223 である。差をさらに広げれば損失は下がる。

    論文タイトルの意味。 Shervine が式の説明前に触れたのが、DPO 論文のタイトル “Direct Preference Optimization: Your Language Model is Secretly a Reward Model”（あなたの言語モデルは、実は reward model である）。 「この損失関数から特定できる reward のプレースホルダが、policy の関数として表現されている。 r はどこにもないのに、reward に相当するものを書き下すと、そこにモデルそのものの式が現れる。とても面白い洞察です」。

    周辺情報：β の意味と実装での挙動。 DPO の β は、導出元の KL 正則化目的にある係数と対応し、reference からの逸脱をどれだけ強く抑えるかを表す。 元の RL 目的では大きい β ほど KL 罰則が強く、最適 policy は reference に近くなる。 DPO 損失の中では同じ β が log 比の差を拡大・縮小するため、単なる学習率ではない。 Shervine は 「オーダー感としては典型的に 0.1 程度」と述べたが、適切な値はデータと実装に依存する。 最適化対象は policy のみで、reference は固定し、選好ペアを入力する。 Hugging Face TRL の DPOTrainer 公式ドキュメントも同じ形の損失を掲げ、 β > 0 を「選好シグナルの強さを制御するハイパーパラメータ」と説明している。 さらに興味深い実装上の観察として、同ドキュメントは 「実際には、好ましい completion の尤度を上げるというより、好ましくない completion の尤度を抑えることで目的が達成されることが多い」 と記している ― §2 の「負のシグナルを注入する」という講義の主題が、実装レベルでも観測されているということである。 なお TRL は rewards/chosen = β log(πθ(y⁺|x) / πref(y⁺|x)) を 「暗黙の reward（implicit reward）」としてログに出しており、 「言語モデルが密かに reward model である」という論文タイトルがそのまま指標名になっている。

    18. DPO はどこから来たのか ― 5 ステップの導出

    この節では、DPO の式を暗記する代わりに、KL 正則化付きの reward 最大化から 5 段階で導く。 最適 policy を解析的に解き、reward を policy と reference の log 尤度比へ書き換え、Bradley-Terry へ代入する。 すると、全回答を足し上げる必要がある partition function（分配関数）Z(x)が 同じ質問内の差で相殺され、reward model も Z(x) の計算も不要になる。

    maxπ 𝔼x∼𝒟, y∼π(·|x)[r(x,y)] − β DKL(π(·|x) ‖ πref(·|x)) 出発点。π は求めたい policy、π_ref は固定した reference、r は仮想的な真の reward、β>0 は KL 罰則の重み
    flowchart TB S1["① PPO の目的関数から出発
    reward 最大化 − β·KL(π_θ ‖ π_ref)"] S2["② 最適 policy π* を解析的に導く
    π*(y|x) ∝ π_ref(y|x)·exp(r(x,y)/β)
    （Z(x) は分配関数＝正規化項）"] S3["③ 式を並べ替え、r を π* の関数として表す
    r(x,y) = β log(π*(y|x)/π_ref(y|x)) + β log Z(x)"] S4["④ この「reward」を Bradley-Terry に代入
    → Z(x) が相殺し、reward が消える"] S5["⑤ 確率を損失関数に変換
    （最尤 → 負の対数尤度）= DPO 損失"] S1 --> S2 --> S3 --> S4 --> S5

    クリックで拡大。DPO 損失が導かれるまでの 5 ステップ（講義スライドの構成に基づく）。

    各ステップの中身

    1. KL 正則化付き RLHF 目的から出発する。 「数枚前のスライドで見た PPO の目的関数を思い出してください。reward を最大化し、得られた policy と reference policy の距離を最小化したい。 この reward 最大化と KL divergence 項のトレードオフです。そして β 係数が、ベースモデルからどれだけ離れることを罰するかを制御していました」
    2. 最適解を解析的に求める。 「この論文がやったのは、この式を書き下し、最適解が何かを解いたこと。最適 policy π* を表現し、それを r の関数として導出した」。 質問 x ごとに確率の和が 1 になる制約を入れて解くと、 π*(y|x)=πref(y|x)exp(r(x,y)/β)/Z(x) を得る。 Shervine が強調したのは、ここが追加の経験則ではなく解析的な式変形だという点である。
    3. 「reward」の項を特定する。 式に現れる Z(x)=Σyπref(y|x)exp(r(x,y)/β) は partition function（分配関数）で、未正規化の重みを確率へ直すための和である。 「新しく出てきたものではなく、もともと式にあった項の関数」。 対数を取って並べ替えると r(x,y)=βlog(π*(y|x)/πref(y|x))+βlog Z(x) となり、 reward を最適 policy の関数として書ける。
    4. その「reward」で Bradley-Terry を書く。 これが この論文の鍵だと Shervine は言う。 「Bradley-Terry の定式化を再び取り、そこに、先ほど得た最適 reward の式（= policy の関数）を代入した。 結果、独立した reward はもう存在せず、β、policy、reference だけが残る」。 同じ質問 x について chosen と rejected の reward を引くので、 両方に共通する βlog Z(x) は正確に 0 へ相殺される。
    5. 損失関数に変換する。 得られた選好確率の積を最大化し、対数を取り、負号を付けて最小化へ変える。 「Afshin が説明したのと同じ手順」、すなわち §9 の MLE → NLL をもう一度適用したものが §17 の DPO 損失である。

    周辺情報：なぜ partition function Z(x) が消えるのか。 ステップ ③ で得られる reward には β log Z(x) という項が残るが、Z(x) は プロンプト x にのみ依存し、応答 y には依存しない。 Bradley-Terry は r(x, yw) − r(x, yl) という同じ x の下での差しか使わないため、この項は綺麗に相殺される。 これが DPO 成立の核心的なトリックであり、 「Z(x) を計算しなくてよい ＝ 全応答にわたる和を取らなくてよい」からこそ、reward model なしで学習が回る。 §8 で述べた「Bradley-Terry では絶対値ではなく差だけが意味を持つ」という性質が、ここで最大限に活かされている。

    一次論文に照らした用語の補正。 講義は導出の出発点を分かりやすく「PPO objective」と呼ぶが、DPO 原論文が直接解くのは 一般の KL 制約付き reward 最大化目的であり、PPO-Clip の代理目的そのものを解析的に解くわけではない。 PPO はその RLHF 目的を数値的に最適化する代表的手段、DPO は同じ目的の最適解と Bradley-Terry を使って変数変換する手段、と区別すると正確である。 また原論文の「追加の仮定なし」という趣旨はこの代数変形についてであり、全体としては人間選好を Bradley-Terry で表す仮定を使っている。

    • Q：ベースモデルに対してパラメータを最適化しているのか？ ― 「はい、ただしベースモデルではなく現在のモデルです。ベースモデルはイテレーションを通じて固定されていて、損失関数の中に登場する。 更新するのはもう一方のパラメータで、それが preference tune されたモデルになる。重みの集合は 2 つ ― 1 つは凍結、1 つは更新」
    • Q：reference model の代わりに別の大きなモデルを使ってもよいか？ ― 「面白い論点だが、それは別のアルゴリズムになると思う。 preference tuning の段階は、これまで学んできたものに対して応答を揃える営み。 違うモデルから始めて違う確率分布を preference tune すると、損失の観点で意味が通らないことをしてしまうかもしれない。 全体の要点は最後に学習したチェックポイントから始めて、そこからさらに completion の分布を preference tune することだと思う」

    19. RLHF と DPO ― どちらを選ぶか

    この節では、PPO ベース RLHF と DPO を、必要なモデル、データの作られ方、安定性、性能、費用で比べる。 DPO は固定した選好ペアから直接学べるため簡単だが、更新後の policy が作る回答と学習データがずれる distribution shift（分布シフト）を抱える。PPO は現在の policy に近い回答を毎回採点できるが、そのぶん複雑で高価になる。 講義と参照論文の性能主張を分けたうえで、実務的な選び方を整理する。

    観点PPO ベース RLHFDPO
    学習の構造多段階（reward model → policy 更新）教師あり学習の単一ステップ
    必要なモデル数4（policy, value, reward, base）2（policy πθ と reference πref）
    学習の安定性reward・value 推定と on-policy 生成が絡み、調整が難しい分類損失として直接学べるため比較的安定
    データの由来
    （本レポートによる補足）    		基本的に on-policy。現在に近い policy から rollout を作る固定の選好データを使う offline 手法。広い意味では off-policy 側だが、古典的 off-policy RL ではない
    性能絶対的なコンセンサスなし。タスクによって異なり、実装に敏感

    DPO の固有の弱点 ― 分布シフト

    「そんなに簡単なら、なぜみんな DPO を使わないのか？」という当然の疑問に、Shervine はこう答えた。

    そう簡単ではありません。実際には各手法に一長一短があります。大枠としては PPO のほうが DPO より性能が良い。 そして DPO の良さである「直接的な教師信号」は、モデルが学習時に見た分布とは正確には一致しないものにフィットしてしまうという代償を伴うことがある。

    たとえば選好データが古い SFT model の短い回答だけで作られているのに、更新後の policy が長い推論回答を出すようになれば、 学習時に比較した領域と実際の生成領域がずれる。DPO はその新しい領域で人間が何を好むかを自動では観測しない。 つまり 「既存の選好データをそのまま再利用できる」という利点の裏返しが分布シフトである。 緩和策としては 選好関連データで先に SFT をしておく、あるいは 自分で生成して自分で評価する方法があるが、 「それはまた別のコストを払うことになる」。

    周辺情報：参照論文が実際に主張していること。 スライド脚注の “Is DPO Superior to PPO for LLM Alignment? A Comprehensive Study”（Xu et al., 2024／arXiv:2404.10719）は、 まさにこの問いを正面から扱った論文である。アブストラクトの要点は次のとおり ― ChatGPT や Claude のような実サービスは reward ベース（PPO）を使う一方、学術ベンチマークの SOTA は reward-free（DPO）で達成されることが多いという捻れがある。 論文は理論・実験の両面から DPO には根本的な限界がありうることを示し、PPO の性能を引き出す鍵となる要因を洗い出したうえで、 対話からコード生成までの一連のテストベッドで比較し、「PPO はすべてのケースで他の alignment 手法を上回り、難度の高いコードコンペティションで SOTA を達成した」と報告している。 講義の「大枠では PPO のほうが良い」という表現は、この論文の結論に沿ったものである。

    性能について断定しないための一次資料上の整理。 講義スライド自体は「絶対的な共通見解はなく、タスクと実装に依存する」と明記する。 講義が引用した Xu et al. (2024) は同論文の条件で PPO が全比較を上回ったと報告する一方、 DPO 原論文は感情制御で PPO を上回り、要約と単発対話で同等以上だったと報告している。 データ、reward、計算予算、実装が違う結果を横断して「PPO が常に上」「DPO が常に上」と一般化することはできない。 本節の引用は登壇者と各論文の主張を伝えるもので、普遍的な順位を確定するものではない。

    実務的な使い分け ― Shervine の結論

    「トレードオフは何か、実際にはどちらが使われるのか」という最後の質問への回答が、この講義の実務的な結論である。

    すべては計算資源の予算と、どこまで性能にこだわるか、どこまで学習プロセスの子守りをする覚悟があるか次第です。 PPO ― RL の部分 ― は正しくチューニングするのが非常に難しい。最も高い結果を出すが、はるかに少ない労力でほぼその水準に到達できることもある。 素早く preference tuning したい、良い結果は出るが最良ではないかもしれない、というなら DPO が友達です。 強化学習のエキスパートで、自分が何をしているか分かっていて、最後の 1 滴まで性能を絞りたいなら、PPO のほうが良い道かもしれません。

    22. 難しい用語の補足（用語集）

    本節では、本文で初出時に説明した alignment、reward model、PPO、DPO などの専門語を、定義と講義内での役割から引き直せる形で集約する。 ここは講義の発言そのものではなく、一次資料に基づく本レポートの補足である。

    用語意味この講義での位置づけ
    alignment（整合）モデルの振る舞いを人間の意図・価値観に合わせることpreference tuning はこの alignment の実装手段のひとつ
    preference tuning（選好調整）好ましい／好ましくない応答の比較を学習信号にし、既存能力の使い方・安全性・トーンを調整する工程SFT が表しにくい「これは出すな」という負のシグナルを与える
    preference pair同一プロンプトに対する「好まれた応答 yw」と「好まれなかった応答 yl」の組reward model 学習と DPO の唯一の入力データ
    policy（方策）状態から行動への（確率的な）写像。LLM では次 token の確率分布そのもの学習対象。πθ と表記
    old / reference policyold は直前の RL イテレーションの snapshot、reference は通常 SFT 済みベースモデルを固定した基準old は局所的な急更新、reference は学習全体での累積的な逸脱を抑える
    frozen model（凍結モデル）推論には使うが重みを更新しないモデルreward と reference を安定した採点・比較基準として保つ
    rollout / completionモデルがプロンプトに対して生成した応答 1 本まるごとreward はこの単位で与えられる（token 単位ではない）
    reward model (RM)(prompt, response) を入力にスカラースコアを返すモデルStep 1 で学習し、Step 2 では凍結。BoN でも使う
    Bradley-Terry モデルペア比較データから各対象の潜在的な強さを推定する 1952 年の統計モデルreward model の損失も DPO の損失も、この定式化が土台
    sigmoid（logistic 関数）σ(x) = 1/(1+e−x)。実数を (0,1) に写す S 字関数Bradley-Terry の確率表現に現れる。2 クラスの softmax と一致
    最尤推定（MLE）／負の対数尤度（NLL）観測データが最も起きやすくなるパラメータを選ぶ／その対数尤度に負号を付けた損失§9 の黒板導出そのもの。cross entropy はその特殊形
    Kullback-Leibler（KL）divergenceΣ p log(p/q)。2 分布の乖離度。非対称で距離ではない。常に非負（Jensen の不等式）「ベースモデルから離れすぎない」制約の数学的表現
    reward hacking不完全な指標に過剰最適化し、指標は上がるが本来の目的は達成されない現象KL ペナルティを入れる主要な動機。Goodhart の法則の一形態
    破滅的忘却新しい学習によって既習の知識・能力が失われることKL ペナルティを入れるもう一つの動機
    advantage≈ reward − baseline。「期待水準と比べてどれだけ良いか」PPO が実際に最大化する量。分散低減により学習が安定・高速化
    value function部分生成を入力に、policy に従って続けた場合の期待 reward を返す関数（token 単位・回帰）advantage の baseline を供給。policy と同時学習し、4 モデルの 1 つを占める
    GAEGeneralized Advantage Estimation。value function を使って policy gradient の分散を下げる指数重み付き推定量advantage の実際の計算法。講義は範囲外として深入りせず
    policy gradient（方策勾配）行動の対数確率を advantage で重み付けし、期待 reward が増える方向へ policy を直接更新する方法PPO と GRPO の土台。正解 token がない RL でも学習できる
    PPOProximal Policy Optimization。同じデータで複数エポックの更新を回せる policy gradient 法RLHF の Step 2 で最も一般的なアルゴリズム
    policy ratio / clip / ε現在と old policy の確率比を [1−ε, 1+ε] に切り詰め、1 回の更新幅を制限する仕組みPPO-Clip の中核。実装上は ε = 0.2 が事実上の標準
    PPO-KL PenaltyPPO の目的から reference policy との KL divergence を重み β 付きで差し引く変種base からの累積的な逸脱、reward hacking、破滅的忘却を抑える
    β（beta）KL ペナルティの重み。ベースモデルから離れることをどれだけ罰するかPPO と DPO の両方に共通して現れる。DPO では典型的に 0.1 程度
    on-policy / off-policy学習中のモデル自身の生成で学習する／しないPPO は on-policy、SFT や DPO は自前生成に依存しない
    Best-of-N (BoN)N 個生成して reward model で採点し、最良を返す推論時の手法RL 学習を回避できるが、コストを推論時に付け替えるだけ
    DPODirect Preference Optimization。reward model を消し、選好ペアだけで policy を直接最適化する教師あり手法必要モデルは policy と reference の 2 つ
    partition function Z(x)確率分布を正規化するための和。x にのみ依存し y に依存しないBradley-Terry の差分で相殺されるため、DPO では計算不要になる
    分布シフト学習に使うデータの分布が、モデル自身の生成分布とずれることDPO 固有の弱点。既存の選好データセットをそのまま使えることの裏返し
    RLAIFReinforcement Learning from AI Feedback。選好ラベルを人間でなく AI が付けるRLHF の "HF" が人間由来でない場合の呼称
    GRPOGroup Relative Policy Optimization。グループ内の相対 reward を advantage に使い、value model を不要にする PPO の変種DeepSeekMath 論文が導入。次回 Lecture 6 の主題
    LLM-as-a-judge評価基準と候補応答を強力な LLM に渡し、比較採点させる手法。大規模化しやすいが判定モデルの偏りを継承する選好データのラベル付けにおける人手評価の proxy
    BLEU / ROUGEBilingual Evaluation Understudy / Recall-Oriented Understudy for Gisting Evaluation。参照文との n-gram 重なりを測る自動指標機械翻訳／要約向けで、自由な対話の意味的な好ましさには弱い

    23. まとめ ― 各手法はどのボトルネックを解くか

    本節では SFT、PPO ベース RLHF、Best-of-N、DPO、GRPO を、解消するボトルネック・必要モデル数・新たに払うコストの対応で総括する。

    手法解こうとしている問題必要モデル数払うコスト
    SFT のみタスク遂行と振る舞いの型を教える1負のシグナルを表現できない／高品質データの確保がスケールしない
    PPO ベース RLHF選好に沿って policy を直接最適化する42 段階の依存関係・多数のハイパーパラメータ・不安定性・reward hacking
    Best-of-NRL 学習をまるごと回避する2（SFT + RM）推論コストとレイテンシ（無限の予算でも最大値のレイテンシは悪化）
    DPOreward model と RL を消して教師ありにする2分布シフト／大枠では PPO に性能で劣ることがある
    GRPO（次回）PPO から value model を外し、メモリを削る3グループ生成が必要（Lecture 6 で詳説）

    講義を通した一貫したストーリーは 「4 つのモデルを減らす歴史」である。 PPO の 4 モデルに対し、Best-of-N は学習そのものを捨て、DPO は reward model と value model を数式で消し、 GRPO は value model だけを消す。どれが正解かはタスクと予算次第 ― それが Shervine の最終的な答えだった。

    1. 評価とは何を測ることか

    動画 00:00

    前回までに、RAG による外部知識の取得、bi-encoder での候補検索と cross-encoder での再ランキング、tool calling、ReAct の Observe → Plan → Act を扱った。Lecture 8 は、それらを含む LLM システムの性能をどう定量化するかに焦点を移す。

    「LLM を評価する」には、出力の一貫性・事実性・有用性だけでなく、レイテンシ、価格、稼働率などのシステム指標も含み得る。本講義の主対象は出力品質、つまり「実際の応答がどれほど良いか」である。自然言語、コード、数学的推論など出力形式が多様なため、すべてに通用する単一指標を作るのは難しい。

    2. 人手評価と評価者間一致

    動画 07:08

    理想は、各プロンプトに対する各応答を人が毎回採点することだ。しかし「誕生日プレゼントにテディベアを勧める応答は有用か」のような問いでは、評価者によって「十分具体的」「種類まで指定していないので不十分」と判断が割れる。そこで、評価ガイドラインの明確さを測る健康指標として評価者間一致を追跡する。

    単純一致率だけでは不十分である。二人がランダムに Yes/No を半々で選んでも、一致率は 0.5² + 0.5² = 0.5、つまり50%になる。したがって、観測一致率を「偶然でも起こる一致」と比較する必要がある。

    指標想定講義での位置づけ
    単純一致率同じ判定の割合直感的だが、偶然一致を補正しない
    Cohen's κ主に2名の評価者観測一致と偶然一致の差を正規化
    Fleiss' κ複数評価者Cohen's κ を複数評価者へ拡張
    Krippendorff's α複数評価者・欠損等を含む柔軟な設定より一般的な一致度の測定
    運用上の使い方: 一致度が低ければ「評価者が悪い」と結論づけず、評価者同士の alignment session を開き、基準と例を揃える。人手評価の弱点は完全には消えないが、主観性を測定・改善可能な問題に変えられる。

    3. 参照文とルールベース指標

    動画 18:24

    毎回の人手採点を避ける次の案は、プロンプトごとに人が一度だけ理想回答（reference）を作り、モデルを更新するたびに自動比較することだ。自然言語には同じ意味を表す複数の言い方があるため、完全一致ではなく、語や n-gram の重なりを柔軟に測る指標が使われてきた。

    指標主用途中心となる考え方補正
    METEOR機械翻訳unigram の precision / recall を重み付き F-score で統合一致語の並びが分断されるほど chunk penalty。語幹・同義語も一部考慮
    BLEU機械翻訳予測側 n-gram の一致を重視する precision 寄りの指標短い出力で指標を稼ぐのを防ぐ brevity penalty
    ROUGE要約参照要約との n-gram 等の重なり複数の派生形が存在

    共通の弱点は、意味が同じでも表現が異なると低得点になり得ることだ。「plush teddy bear」「soft stuffed bear」「gentle toy companion」は意味が近くても表層一致が少ない。また、人手評価との相関を高めるために多くのハイパーパラメータを調整しても相関は完全ではなく、参照文を作る初期コストも残る。

    4. LLM-as-a-Judge の基本設計

    動画 28:00

    大規模事前学習と選好チューニングを経た LLM は、知識と人間の好みに関する信号を持つ。そこで、評価対象のプロンプト・応答・評価基準を別の LLM に渡し、理由（rationale）とスコアを返させる。ルール指標の数字だけでは分からなかった「なぜその点数なのか」を自然言語で説明できることが大きな違いである。

    実務では、まず理由を出させ、その後にスコアを出させる。この順序は、モデルが判断材料を言語化してから結論を出すため、経験的に品質が上がる。通常の生成では JSON などの形式が保証されないので、guided / constrained decoding に基づくstructured outputを利用し、{ rationale, score } のようなスキーマを強制する。

    Pointwise

    単一応答を「良い / 悪い」「合格 / 不合格」などで評価する。

    Pairwise

    応答 A と B を比較し、どちらが優れているかを選ぶ。

    合成選好データ

    Pairwise Judge の選択を、reward model や preference tuning 用ラベルとして利用できる。

    二つの利点: 正解参照文や人手ラベルがなくても評価を開始できること、スコアと一緒に解釈可能な理由を得られること。ただし「人手不要」ではなく、後述する校正のために人手評価は依然重要である。

    5. Judge の3大バイアス

    動画 38:47
    バイアス症状主な対策
    位置バイアスPairwise 比較で先に置かれた A を選びやすいA/B と B/A の両順序で評価し、結果の一致や多数決を見る
    冗長性バイアス正確さではなく、長く詳細な応答を好む長さを評価しないと明記、few-shot で例示、必要なら長さペナルティ
    自己強化バイアスJudge と同じモデルが生成した応答を好む生成モデルと Judge を分け、可能ならより高能力な Judge を使う

    この三つは網羅的ではない。特定ラベルへの偏りや、人間の選好そのものとの不一致もあり得る。また、別モデルでも学習データが似ていれば完全に独立とは限らない。それでも、生成器と Judge を同一にしないことはリスク低減になる。Judge は必ず大きくなければならないわけではないが、微妙な違いを見抜くには、より強い推論能力を持つモデルがよく使われる。

    6. LLM Judge のベストプラクティス

    動画 47:22
    実践理由
    評価基準を crisp にする欲しいもの・避けたいものを明示し、主観的な解釈余地を減らす
    二値スケールを優先多段階採点より Judge と人間の双方が判断しやすく、余計なノイズを減らせる
    理由を先に出す判断材料を外化してからスコアを確定させる
    既知のバイアスを検査・緩和位置入れ替え、長さの明示、別モデル利用などを評価系に組み込む
    人手評価と校正するJudge は人間の選好の代理なので、相関分析でずれを確認しプロンプトを改善する
    低温度を使うtemperature = 0.1〜0.2 程度で再現性を高める
    Judge の点数を上げること自体が目的になると、人間の評価とはずれた代理指標へ最適化してしまう。Judge と人手の乖離を継続監視する必要がある。

    評価軸は大きく、タスク性能（有用性、事実性、関連性など）と、出力の整合性（トーン、スタイル、安全性など）に分けられる。何を測るかを先に定義し、異なる軸を一つの曖昧なスコアへ潰しすぎないことが重要である。

    7. 事実性は「原子化してから測る」

    動画 54:06

    文章全体を単純な合格 / 不合格で判定すると、一部だけ誤っている長文のニュアンスを失う。講義の例文「テディベアは1920年代に作られ、捕らえた熊を誇らしげに撃とうとした Theodore Roosevelt にちなむ」には、年代（実際は1900年代）と行動（Roosevelt は撃つことを拒否）の二つの誤りがある一方、名前の由来など正しい事実も含まれる。

    flowchart LR A[自由形式の応答] --> B[LLMで原子的な事実へ分解] B --> C1[Fact 1] B --> C2[Fact 2] B --> C3[Fact 3] B --> C4[Fact 4] C1 --> D[RAG / Web検索で二値検証] C2 --> D C3 --> D C4 --> D D --> E[重要度で重み付けして集約] E --> F[文章全体の事実性スコア]
    1. 複数文・複数段落の応答を、検証可能な事実の一覧へ分解する。
    2. 各事実を RAG、Web 検索、知識ベースなどで確認し、基本は正誤の二値で判定する。
    3. 事実ごとの重要度を重みとして、正しい事実の割合を集約する。重みはすべて同一でもよい。

    この設計により「二つ誤りがあるが、残りは正しい」という部分点を表現できる。重要な主張の誤りを、周辺的な細部の誤りより重く扱うことも可能になる。

    8. エージェントは段階別に評価する

    動画 1:00:15

    エージェントは Observe → Plan → Act のループを繰り返すため、最終回答だけを見ても根本原因が分からない。一回の tool calling を、ツール予測、ツール実行、結果の統合へ分け、それぞれの失敗を分類する。

    flowchart LR U[ユーザー要求] --> P[1. ツール名と引数を予測] P --> X[2. ツールを実行] X --> S[3. 結果から応答を統合] S --> A[ユーザーへ回答] S -.次の行動が必要.-> P
    診断の原則: 失敗例を個別の珍事件として追うのではなく、共通する失敗モードへ分類し、同じ原因の群をまとめて直す。エージェント評価ではこの方法論が特に重要になる。

    9. ツール予測の4つの失敗

    動画 1:02:19
    失敗モード考えられる原因改善策
    必要なツールを使わず punt するtool router の recall 不足、または LLM が利用判断を学べていないrouter の recall 改善、SFT 例の追加、プロンプト修正
    存在しないツール名を生成モデルが弱い、上位指示が曖昧、API 名・引数・説明が不自然まず水平指示と API 設計を点検し、必要ならモデルを強化
    存在するが不適切なツールを選択ツール間のスコープが競合、router が候補を落としている適用条件を明記し、API の責務を分離、router を調整
    ツールは正しいが引数が誤る位置情報など必要な文脈がない、引数の意味が不明瞭先行ツールで情報取得、権限エラーを明示、API / SFT / prompt を改善

    tool router は、すべての API 定義を毎回コンテキストに入れないための候補絞り込みである。コンテキストを節約しつつ必要なツールを落とさない必要があるため、precision よりrecall を重視する。問題が router か LLM 本体かを分けて測らないと、誤った層を修正してしまう。

    10. 実行と応答統合の3つの失敗

    動画 1:14:12
    段階失敗実務的な対策
    ツール実行実装バグや不明瞭なエラーを返す通常のソフトウェアとして修正。ユーザーが行動できる構造化結果へ変換する
    ツール実行応答を何も返さない副作用の成功・失敗を必ず明示。該当なしでも {} など意味のある空結果を返す
    応答統合正しい結果を誤読・無視するモデル強化、出力量の削減、意味のあるクラス名・属性・構造へ整形

    特に副作用のあるツールが何も返さないと、モデルは成功したか判断できず、偽の成功確認を生成し得る。また、情報が多すぎる出力では重要情報が「海に沈む」。ツール出力は人間向けログの投げ込みではなく、次の LLM ステップが利用しやすい最小限の構造化データにする。

    七つの失敗は、最終的にモデル能力、コンテキストの関連性、tool router / API の設計・学習、ツール実装の四領域へ整理できる。原因の層を特定してから対処することが、エージェントのデバッグを再現可能にする。

    11. ベンチマークの設計原則

    動画 1:23:50

    モデル同士を比較する公開ベンチマークは、自由形式の回答をそのまま別の LLM に判定させるより、可能な限り答えを機械的に採点できる形式を選ぶ。Judge を挟むと、Judge 自身の誤差が新たな層として加わるためである。

    能力領域代表例出力 / 採点主に見るもの
    知識MMLU4択、正解文字の一致広範な事前学習知識の保持
    数学推論AIME3桁の数値難しい問題を解く推論能力

    12. 知識評価: MMLU

    動画 1:25:12

    MMLU（Massive Multitask Language Understanding）は約60の多様なタスクを含み、日常知識から法律、医学まで幅広い。問題と4つの選択肢を提示し、モデルに正解の文字を出させるため、採点を標準化できる。

    純粋な論理だけでは解けず、各分野の事前知識を必要とする設問が多い。そのため、主として「大規模コーパスで事前学習した情報を、推論時にどれだけ取り出せるか」を測る。ただし、特定分野の専門能力を一つの平均値だけで表すものではない。

    13. 推論評価: AIME と PIQA

    動画 1:29:34

    AIME: 数学推論

    AIME は数学オリンピックを目指す高校生向けの難しい試験で、問題文に対して3桁の整数を答える。回答形式が厳密なので採点は容易だが、答えに至るには途中の推論が必要であり、reasoning model の能力を測りやすい。

    PIQA: 物理世界の常識推論

    PIQA（Physical Interaction: Question Answering）は、日常の物理世界に根ざした約2万件の二択問題を持つ。講義では「カーペットで失くした小物を見つけるには、密閉した掃除機より吸入口にヘアネットを付ける」という例を挙げた。数学知識ではなく、物や空気がどう振る舞うかという常識を問う。

    14. コード評価: SWE-bench

    動画 1:33:57

    コーディング能力は、AI 支援開発そのものだけでなく、エージェントが Python 等で書かれたツールを読み、呼び出し、出力を解釈するためにも重要である。SWE-bench は、人気の Python リポジトリから、issue を解決しテストも追加した pull request を抽出する。

    1. モデルへコードベースと issue を与える。
    2. モデルが修正パッチを生成する。
    3. パッチを適用し、関連テストが通るかで解決を判定する。

    実際の issue とリポジトリを使い、テストによる before / after を得られるため、表面的なコード生成ではなくソフトウェア工学タスクの完遂を測れる。

    15. 安全性評価: HarmBench

    動画 1:36:15

    安全性は各プロバイダーのポリシーに依存し、全社が同じ目標を採用しているとは限らない。そのためモデルカードには安全性評価が載っても、単一スコアで横並び比較しにくい。ベンチマークを使う前に、その中身が自社ポリシーと合うかを確認する必要がある。

    HarmBench の区分対象
    Standard一般的な有害行動
    Copyright望ましくない著作物の生成
    Contextualテキスト文脈によって有害となる行動
    Multimodalテキスト以外のモダリティを含む文脈依存の有害行動

    自由形式の有害応答は regex だけでは判定できないため、HarmBench は専用 classifier を使う。重要なのは、モデルが実行能力不足で失敗しても、有害行動を試みたなら攻撃成功と数える点である。これは「能力の高さ」と「安全性」を分離する。一方で classifier 自身の誤差が入る点は、固定正解で採点できる他のベンチマークとの違いである。

    16. エージェント評価: τ-bench

    動画 1:40:51

    τ-bench は航空と小売の二領域で、ツール群、守るべきポリシー、ユーザーのタスクを提供する。対話は前のターンに依存するため、別の大規模 LLM がユーザー役をシミュレートし、評価対象エージェントと複数ターン対話する。

    たとえばフライト変更では、最終的なデータベース状態や、キャンセルなど要求されたアクションが実現したかで reward を計算する。会話が自然だったかだけでなく、実世界の状態が正しく変わったかで判定する点が重要である。

    指標意味適した問い
    pass@kk回のうち少なくとも1回成功する確率候補を複数試せる問題で、成功解を見つけられるか
    passkk回すべてが成功する確率ユーザー対応を自動化できるほど一貫して信頼できるか
    エージェントで重要なのは反復信頼性: 一度だけ成功するデモではなく、同じタスクを何度実行しても成功することが運用投入の条件になる。そのため τ-bench は passk を重視する。

    17. ベンチマークをモデル選定へつなぐ

    動画 1:45:14

    ベンチマークはモデルを「全面的に良い / 悪い」と決めるものではなく、能力プロファイルを描くものだ。あるモデルはコードに強く、別のモデルは高速・低価格かもしれない。価格、安全性、コンテキスト長など、実際に重視する軸と性能を並べ、ある軸を改善するために他を犠牲にしない選択肢の境界、つまりPareto frontierを見る。

    データ汚染

    モデルが問題や正解を学習中に見ていれば、ベンチマークは能力を正しく測れない。hash、Web blocklist、新しい試験問題などで漏洩を抑える。

    Goodhart の法則

    「測定値が目標になると、良い測定値ではなくなる」。公開指標への過剰最適化を疑う。

    実体験との接続

    Chatbot Arena のような人間選好も参考にしつつ、最後は自分のデータとタスクで候補モデルを試す。

    公開ベンチマークの点数は「あなたの用途に最適か」を直接は答えない。評価対象、採点方法、データ汚染、運用コストを理解したうえで、実タスク評価と組み合わせる。
